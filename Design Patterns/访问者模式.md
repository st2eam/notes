# 访问者模式
> 行为型设计模式

访问者模式 ## 介绍 访问者模式 是一种行为设计模式， 它能将算法与其所作用的对象隔离开来。 ## 结构 访问者 （Visitor） 接口声明了一系列以对象结构的具体元素为参数的访问者方法。 如果编程语言支持重载， 这些方法的名称可以是相同的， 但是其参数一定是不同的。 具体访问者 （Concrete Visitor） 会为不同的具体元素类实现相同行为的几个不同版本。 元素 （Element） 接口声明了一个方法来 “接收” 访问者。 该方法必须有一个参数被声明为访问者接口类型。 具体元素 （Concrete Element） 必须实现接收方法。 该方法的目的是根据当前元素类将其调用重定向到相应访问者的方法。 请注意， 即使元素基类实现了该方法， 所有子类都必须对其进行重写并调用访问者对象中的合适方法。 客户端 （Client） 通常会作为集合或其他复杂对象 （例如一个 组合 树） 的代表。 客户端通常不知晓所有的具体元素类， 因为它们会通过抽象接口与集合中的对象进行交互。 ## 问题 假设我们正在开发 数据报表模块 的二期需求。在这一次需求中，添加了数据的 导出模式 。可以将用户所选择的节点，导出为 智能文档/图片。 这些工作最初看上去非常简单。 你计划为每个节点类添加导出函数， 然后遍历执行每个节点的导出函数。 解决方案简单且优雅： 使用多态机制可以让导出方法的调用代码不会和具体的节点类相耦合。 所有节点的类中都必须添加导出为 智能文档/图片 的方法， 但如果在修改代码的过程中引入了任何缺陷， 那么整个程序都会面临风险。 还有另一个原因， 那就是在此项任务完成后， 产品很有可能会要求程序提供导出其他类型文件的功能， 或者提出其他奇怪的要求。 这样你很可能会被迫再次修改这些重要但脆弱的类。 ## 解决方案 访问者模式建议将新行为放入一个名为 访问者 的独立类中， 而不是试图将其整合到已有类中。 现在， 需要执行操作的原始对象将作为参数被传递给访问者中的方法， 让方法能访问对象所包含的一切必要数据。 class ExportVisitor implements IVisitor{ visitHeaderNode(node) { …… } visitParagraphNode(node) { …… } visitImageNode(node) { …… } ... } 你可能会问，我们为什么不使用方法重载？ 虽然JavaScript 不支持传统意义上的方法重载，但是可以通过以下方法模拟一下。为了可以挑选出能够处理特定对象的访问者方法， 我们需要对它的类进行检查。 这是不是听上去像个噩梦呢？ class Paragraph implements Node{} class HeaderNode extends Paragraph{} class Image implements Node{} elements.forEach(element =&gt; { if (element instanceof Paragraph) return exportVisitor.visitParagraphNode(element) if (element instanceof Header) return exportVisitor.visitHeaderNode(element) if (element instanceof Image) return exportVisitor.visitImageNode(element) // …… }); // 在这里Header将会在第一次判断中直接返回 如果类中存在继承关系，那么判断就会产生错误。 访问者模式使用了一种名为 双分派 的技巧， 不使用累赘的条件语句也可下执行正确的方法。 与其让客户端来选择调用正确版本的方法， 不如将选择权委派给作为参数传递给访问者的对象。 由于该对象知晓其自身的类， 因此能更自然地在访问者中选出正确的方法。 它们会“接收”一个访问者并告诉其应执行的访问者方法。 class Header implements IElement{ accept(visitor) { visitor.visitHeaderNode(this); } } class Image implements IElement{ accept(visitor) { visitor.visitImageNode(this); } } elements.forEach(element =&gt; { element.accept(visitor); }); 为什么是 element.accept(visitor) ，而不是 visitor.visit(element) ？ 在访问者模式中，使用 element.accept(visitor) 而不是 visitor.visit(element) 是为了实现 双分派 （Double Dispatch），这是访问者模式的核心机制。以下是具体原因： 1. 双分派的实现 单一派发 ： visitor.visit(element) 只会根据 visitor 的类型调用相应的方法，这意味着它只处理一个对象的类型（即访问者）。 双重派发 ： element.accept(visitor) 先根据 element 的类型调用 accept 方法，然后在 accept 方法内部调用 visitor.visit(this) 。这确保了方法调用依赖于两个对象的类型： element 和 visitor 。这样，具体调用哪个 visit 方法取决于两个对象的类型。 2. 动态行为 使用 element.accept(visitor) 允许元素自身决定如何处理访问者。这种设计使得每个元素类可以实现自己的 accept 方法，并在其中调用相应的访问者方法，从而实现特定的处理逻辑。 3. 扩展性 通过这种方式，添加新的元素类或访问者类都不会影响现有的代码结构。你可以为新的元素实现 accept 方法，并为新的访问者实现相应的 visit 方法，而不需要修改已有的逻辑。 总结 使用 element.accept(visitor) 是访问者模式中实现双分派的关键，它允许根据两个对象的类型动态决定调用哪个方法，增强了代码的灵活性和可扩展性 ## 与其他模式的关系 你可以将 访问者模式 视为 命令模式 的加强版本， 其对象可对不同类的多种对象执行操作。 你可以使用 访问者 对整个 组合模式 树执行操作。 可以同时使用 访问者 和 迭代器模式 来遍历复杂数据结构， 并对其中的元素执行所需操作， 即使这些元素所属的类完全不同。 ## 优缺点 ✔️ 开闭原则 。 你可以引入在不同类对象上执行的新行为， 且无需对这些类做出修改。 ✔️ 单一职责原则 。 可将同一行为的不同版本移到同一个类中。 ✔️ 访问者对象可以在与各种对象交互时收集一些有用的信息。 当你想要遍历一些复杂的对象结构 （例如对象树）， 并在结构中的每个对象上应用访问者时， 这些信息可能会有所帮助。 ❌ 每次在元素层次结构中添加或移除一个类时， 你都要更新所有的访问者。 ❌ 在访问者同某个元素进行交互时， 它们可能没有访问元素私有成员变量和方法的必要权限。 ## 实战示例 处理复杂结构 用户界面的组件树、文档对象模型（DOM）、抽象语法树（AST）等。访问者模式可以有效地遍历这些结构，执行不同的操作 动态扩展操作 当需要添加新功能时，只需创建新的访问者，如 ImageVisitor ，处理新的逻辑。
