# 适配器模式

> 结构型设计模式

## 介绍

适配器模式是一种结构型设计模式，它能使接口不兼容的对象能够相互合作。

## 结构

- **客户端（Client）**：是包含当前程序业务逻辑的类。
- **客户端接口（Client Interface）**：描述了其他类与客户端代码合作时必须遵循的协议。
- **服务（Service）**：中有一些功能类（通常来自第三方或遗留系统）。客户端与其接口不兼容，因此无法直接调用其功能。
- **适配器（Adapter）**：是一个可以同时与客户端和服务交互的类。它在实现客户端接口的同时封装了服务对象。适配器接受客户端通过适配器接口发起的调用，并将其转换为适用于被封装服务对象的调用。

客户端代码只需通过接口与适配器交互即可，无需与具体的适配器类耦合。因此，你可以向程序中添加新类型的适配器而无需修改已有代码。这在服务类的接口被更改或替换时很有用：你无需修改客户端代码就可以创建新的适配器类。

## 问题

在软件开发中，经常会遇到需要复用现有类的情况，但这些现有类的接口与当前系统要求的接口不一致，导致无法直接使用。例如，一个第三方日志库提供了 `logMessage(msg)` 方法，而你的系统期望的是 `writeLog(level, msg)` 接口。直接修改第三方库是不现实的，而修改现有系统的接口又可能引发大规模的连锁改动。

## 解决方案

适配器模式通过创建一个中间层（适配器类）来解决接口不兼容问题。适配器实现目标接口，同时在内部持有被适配者的引用，将对目标接口的调用转换为对被适配者的调用。

这样，原本因接口不兼容而无法协作的类就可以一起工作了，而且客户端代码不需要任何修改。

## 与其他模式的关系

- **桥接模式**通常会在开发前期进行设计，使你能够将程序的各个部分独立开来以便开发。另一方面，**适配器模式**通常在已有程序中使用，让相互不兼容的类能很好地合作。
- **适配器**可以对已有对象的接口进行修改，**装饰模式**则能在不改变对象接口的前提下强化对象功能。此外，装饰还支持递归组合，适配器则无法实现。
- **适配器**能为被封装对象提供不同的接口，**代理模式**能为对象提供相同的接口，**装饰**则能为对象提供加强的接口。
- **外观模式**为现有对象定义了一个新接口，**适配器**则会试图运用已有的接口。适配器通常只封装一个对象，外观通常会作用于整个对象子系统上。

## 优缺点

- ✅ 单一职责原则：你可以将接口或数据转换代码从程序主要业务逻辑中分离。
- ✅ 开闭原则：你可以在不修改现有客户端代码的情况下在程序中添加新类型的适配器。
- ❌ 代码整体复杂度增加：你需要新增一系列接口和类。有时直接更改服务类使其与其他代码兼容会更简单。

## 实战示例

```typescript
// 第三方日志库（Service / Adaptee）
class ThirdPartyLogger {
    logMessage(msg: string): void {
        console.log(`[ThirdParty] ${msg}`);
    }
}

// 目标接口（Client Interface）
interface ILogger {
    writeLog(level: string, message: string): void;
}

// 适配器（Adapter）
class LoggerAdapter implements ILogger {
    private logger: ThirdPartyLogger;

    constructor(logger: ThirdPartyLogger) {
        this.logger = logger;
    }

    writeLog(level: string, message: string): void {
        // 将目标接口的调用转换为对 ThirdPartyLogger 的调用
        this.logger.logMessage(`[${level}] ${message}`);
    }
}

// 客户端代码
const logger: ILogger = new LoggerAdapter(new ThirdPartyLogger());
logger.writeLog('INFO', '系统启动成功');
```
