# 设计模式概述

> 参考：[refactoringguru.cn](https://refactoringguru.cn/) · 深入设计模式 - 亚历山大 · 什韦茨

## 什么是设计模式

设计模式是一套被反复使用的、多数人知晓的、经过分类编目的**代码设计经验的总结**。使用设计模式是为了重用代码、让代码更容易被他人理解、保证代码可靠性。

设计模式的本质是面向对象设计原则的实际运用，是对类的封装性、继承性、多态性以及关联关系和组合关系的充分理解。

> 活字印刷术、业务和界面分离

## 为什么要学习设计模式

设计模式提供了可复用的解决方案，让代码更容易被他人理解，保证代码可靠性。项目中合理地运用设计模式可以帮你构建灵活的系统，更容易适应变化和扩展。

> 易维护、易扩展、易复用、灵活性好

设计模式不必被当作一种固定的规则或模板来强制实现，相反，设计模式更是一种**思想**，帮助我们理解如何组织代码和解决问题。现代化的前端框架在很多方面都应用了最佳实践，这些组件或函数的设计使用了什么设计模式，值得慢慢观察和总结。

## 设计模式原则 — 高内聚，低耦合

### 1. 单一职责原则（SRP）

> 就一个类而言，应该仅有一个引起它变化的原因。

简单来说就是：**一个函数只做一件事**。

当程序规模不断扩大、变更不断增加后，代码中负责的东西过多会让你对代码失去控制。如果一段代码负责的事情太多，任何一件事发生改变时都会牵一发而动全身。

就像手机拍照和单反相机的区别——手机把相机耦合进了手机，而相机只有拍照这一个职责。大多数时候，产品简单一些、职责单一一些，是更好的选择。

### 2. 开放-封闭原则（OCP）

> 对于扩展是开放的，对于更改是封闭的。

面对需求，对程序的改动通过**增加新代码**进行，而不是更改现有代码。

就像"一国两制"——没有修改原有制度，而是增加了一种新制度。

### 3. 依赖倒转原则（DIP）

> 要面向接口编程，不要面向实现编程。

- 高层模块不应该依赖低层模块，两者都应该依赖抽象
- 抽象不应该依赖细节，细节应该依赖抽象

计算机通过 USB 或蓝牙等标准接口与外设交互，不依赖具体的设备型号。外设设备只要遵循标准接口，就可以在不同计算机上使用。这就是依赖倒转——通过标准接口解耦。

### 4. 里氏代换原则（LSP）

> 子类型必须能够替换掉它们的父类型。

在软件中把父类替换成子类，程序的行为不应有变化。俗话说"老鼠的儿子会打洞"——如果老鼠儿子会上天，没问题，但必须会打洞，不会打洞就违反了该原则。

### 5. 迪米特法则（LoD）

> 一个类对自己依赖的类知道的越少越好。只和朋友通信，不和陌生人交流。

- 前端页面只需调用 API 模块中定义的方法，不需要知道服务端接口的具体细节
- 按钮组件和列表组件通过父组件（中介）协同工作，彼此互不知道对方的存在
- [外观模式](./外观模式.md)是迪米特法则的一个典型应用

### 6. 接口隔离原则（ISP）

> 客户端不应该依赖它不需要的接口。

更好的方法是将臃肿的接口拆分为多个精细接口。能够实现原始接口的类改为实现多个精细接口，其他类仅实现对自己有意义的接口。

与其他原则一样，不要过度使用。创建的接口越多，代码越复杂，需要保持平衡。

### 7. 合成复用原则（CARP）

> 优先使用对象组合，而不是继承来达到复用的目的。

- 软件可以通过插件扩展功能，每个插件独立开发、测试和部署
- React 中高阶组件（HOC）是合成复用原则的典型例子

## 对象之间的关系

| 关系 | 说明 |
|------|------|
| **依赖** | 对类 B 的修改会影响到类 A |
| **关联** | 对象 A 知道对象 B |
| **聚合** | 对象 A 知道对象 B，且由 B 构成 |
| **组合** | 对象 A 知道对象 B、由 B 构成，且管理 B 的生命周期 |
| **实现** | 类 A 定义的方法由接口 B 声明 |
| **继承** | 类 A 继承类 B 的接口和实现，可以对其进行扩展 |

## 设计模式分类

### 创建型模式（6 种）

| 模式 | 一句话描述 |
|------|-----------|
| [简单工厂模式](./简单工厂模式.md) | 通过一个静态工厂方法，根据条件生产不同类型的对象 |
| [工厂方法模式](./工厂模式.md) | 父类提供创建对象的方法，子类决定实例化的类型 |
| [抽象工厂模式](./抽象工厂模式.md) | 创建一系列相关对象，无需指定具体类 |
| [单例模式](./单例模式.md) | 保证一个类只有一个实例，提供全局访问点 |
| [建造者模式](./建造者模式.md) | 将复杂对象的构建与表示分离，同样过程可创建不同表示 |
| [原型模式](./原型模式.md) | 用原型实例指定创建对象的种类，通过拷贝创建新对象 |

### 结构型模式（7 种）

| 模式 | 一句话描述 |
|------|-----------|
| [适配器模式](./适配器模式.md) | 将不兼容的接口转换为客户期望的接口 |
| [装饰模式](./装饰模式.md) | 动态给对象增加额外职责，比生成子类更灵活 |
| [代理模式](./代理模式.md) | 为对象提供代理以控制对其的访问 |
| [外观模式](./外观模式.md) | 为复杂子系统提供一个简单的统一接口 |
| [桥接模式](./桥接模式.md) | 将抽象部分与实现部分分离，使它们可以独立变化 |
| [组合模式](./组合模式.md) | 将对象组合成树形结构，统一对待单个和组合对象 |
| [享元模式](./享元模式.md) | 运用共享技术有效支持大量细粒度对象 |

### 行为型模式（11 种）

| 模式 | 一句话描述 |
|------|-----------|
| [策略模式](./策略模式.md) | 定义一系列算法，封装起来使它们可以互相替换 |
| [模板方法模式](./模板方法模式.md) | 定义算法骨架，将具体步骤延迟到子类 |
| [观察者模式](./观察者模式.md) | 一对多依赖，一个对象状态变化时通知所有依赖 |
| [迭代器模式](./迭代器模式.md) | 顺序访问聚合对象的元素，不暴露内部表示 |
| [责任链模式](./责任链模式.md) | 多个对象都有机会处理请求，解耦发送者和接收者 |
| [命令模式](./命令模式.md) | 将请求封装为对象，支持排队、撤销等操作 |
| [备忘录模式](./备忘录模式.md) | 捕获对象内部状态，在对象之外保存以便恢复 |
| [状态模式](./状态模式.md) | 对象内部状态变化时改变行为，看起来像换了类 |
| [访问者模式](./访问者模式.md) | 不改变元素类的前提下定义作用于元素的新操作 |
| [中介者模式](./中介者模式.md) | 用中介对象封装一系列对象交互 |
| [解释器模式](./解释器模式.md) | 给定语言定义文法，用解释器解释句子 |
