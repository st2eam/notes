# 装饰模式

> 结构型设计模式

## 介绍

装饰模式（Decorator Pattern）允许向一个现有对象动态添加新功能，同时不改变其结构。相比生成子类，装饰模式更为灵活。

核心思想：**将对象放入包含行为的特殊封装对象中，为原对象绑定新的行为**。

## 结构

| 角色 | 说明 |
|------|------|
| **组件（Component）** | 声明封装器和被封装对象的公用接口 |
| **具体组件（Concrete Component）** | 被封装对象所属的类，定义了基础行为 |
| **装饰基类（Decorator）** | 拥有指向组件对象的引用，接口与组件一致 |
| **具体装饰（Concrete Decorators）** | 定义可动态添加的额外行为 |

## 问题

假设你在开发一个通知系统。初始只需发站内信，后来要加邮件、短信、微信通知。如果每种组合都建子类：

```
Notifier → EmailNotifier → EmailSmsNotifier → EmailSmsWechatNotifier → ...
```

组合爆炸，根本无法维护。

## 解决方案

```typescript
interface Notifier {
    send(message: string): void;
}

class BaseNotifier implements Notifier {
    send(message: string): void {
        console.log(`发送: ${message}`);
    }
}

// 装饰基类
class NotifierDecorator implements Notifier {
    constructor(protected wrappee: Notifier) {}
    send(message: string): void {
        this.wrappee.send(message);
    }
}

// 具体装饰器
class EmailDecorator extends NotifierDecorator {
    send(message: string): void {
        super.send(message);
        console.log(`[邮件] ${message}`);
    }
}

class SmsDecorator extends NotifierDecorator {
    send(message: string): void {
        super.send(message);
        console.log(`[短信] ${message}`);
    }
}

// 任意组合
const notifier = new SmsDecorator(new EmailDecorator(new BaseNotifier()));
notifier.send("系统告警");
// 输出: 发送: 系统告警 → [邮件] 系统告警 → [短信] 系统告警
```

## 两种实现模式

### 透明模式

客户端完全针对抽象编程，不区分具体构件和具体装饰类型。**优点**：可以对已装饰过的对象进行多次装饰。**缺点**：无法单独调用装饰器新增的方法。

```java
Component c = new ConcreteDecorator2(new ConcreteDecorator1(new ConcreteComponent()));
c.operation();
// 只能调用 operation()，不能调用装饰器特有的 addedBehavior()
```

### 半透明模式

用具体装饰类型定义装饰后的对象。**优点**：可以调用装饰器特有方法。**缺点**：不能实现多次装饰。

```java
ConcreteDecorator c = new ConcreteDecorator(new ConcreteComponent());
c.operation();
c.addedBehavior(); // 可以单独调用新增方法
```

## 与其他模式的关系

| 模式 | 区别 |
|------|------|
| **适配器模式** | 适配器改变对象的**接口**；装饰器不改变接口但**增强功能** |
| **代理模式** | 代理控制对象访问，通常自行管理服务对象生命周期；装饰器的组合由客户端控制 |
| **组合模式** | 都基于递归组合，但装饰器只有单子组件，旨在增加职责而非聚合结果 |
| **策略模式** | 装饰器改变对象的"皮肤"，策略改变对象的"内脏" |

## 优缺点

✔️ 无需创建新子类即可扩展对象行为
✔️ 可以在运行时动态添加或移除职责
✔️ 可以用多个装饰器组合出多种行为
✔️ **单一职责原则**：将庞杂的大类拆分为多个具体装饰类

❌ 在装饰器栈中删除特定装饰器比较困难
❌ 装饰器的顺序会影响最终结果
❌ 多层装饰的初始化代码可能不够优雅

## 实战示例

### React HOC（高阶组件）

```tsx
function withLoading<P>(Component: React.ComponentType<P>) {
    return (props: P & { loading: boolean }) => {
        if (props.loading) return <div>Loading...</div>;
        return <Component {...props} />;
    };
}

function withAuth<P>(Component: React.ComponentType<P>) {
    return (props: P & { hasPermission: boolean }) => {
        if (!props.hasPermission) return <div>无权限</div>;
        return <Component {...props} />;
    };
}

// 叠加
const EnhancedComponent = withAuth(withLoading(MyComponent));
```

### Express 中间件

```typescript
// 每个中间件就是一个装饰器，包装了原始请求处理
app.use(logger);       // 日志
app.use(authenticate); // 认证
app.use(router);       // 核心路由
```

### TypeScript 装饰器

```typescript
function log(target: any, key: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    descriptor.value = function (...args: any[]) {
        console.log(`调用 ${key}，参数:`, args);
        return original.apply(this, args);
    };
}

class Service {
    @log
    getData(id: number) { return { id }; }
}
```
